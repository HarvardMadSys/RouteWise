# 在线实验计划：FreeInference 真实流量服务

本文档总结了 FreeInference 数据集的当前状态，并提出了一个新的在线实验计划。该计划将实验从“历史日志回放（Trace replay）”升级为“真实的在线路由服务（Live serving）”。

### 1.4 各模型“配额稀缺性”分析

要让 Primal-Dual 路由算法发挥价值，每日的流量必须超过设定的配额阈值 $Q$，这样算法才会被迫做出实质性的资源分配决策。

| 模型 | 活跃天数 | 超过 Q=300 的天数 | 超过 Q=2000 的天数 | 超过 Q=5000 的天数 |
|-------|------------|--------------|---------------|---------------|
| llama-3.3-70b | 38 | 19 (50%) | 14 (37%) | 12 (32%) |
| llama-4-scout | 21 | 8 (38%) | 4 (19%) | 3 (14%) |
| glm-4.5 | 12 | 2 (17%) | 1 (8%) | 0 (0%) |
| MiniMax-m2 | 11 | 0 (0%) | 0 (0%) | 0 (0%) |

**核心结论**：只有 `llama-3.3-70b` 和 `llama-4-scout` 的每日流量足够大，能制造出有意义的“配额稀缺性”。`GLM-4.5` 和 `MiniMax` 的流量太稀疏，如果把配额设在 $Q \ge 300$，根本测不出配额受限的场景。

### 1.5 现有的实验方案：历史回放 (Trace Replay)

目前的实验采用的是**离线历史数据回放**：
- 按照历史时间戳顺序重放请求。
- 在线策略（Greedy, Primal-Dual, LA-PD）顺次做出路由决策。
- 离线最优算法（Offline Optimal）以上帝视角算出省钱上限。
- 实验中没有发起真实的 API 调用；所有成本都是根据定价模型推算出来的。

这种方法足以用于比较算法的好坏，但它**无法**体现：
- 真实的实时延迟动态（如 TTFT 和 TPS 的波动）。
- 服务商接口的限流（Rate limiting）和熔断行为。
- 在并发负载下，端到端服务的真实表现。

## 2. 服务商限流阈值摸底 (前提准备)

在开展在线实验前，我们必须先**摸底各个外部服务商的限流阈值（Rate limits）**。我们自己写的路由网关（Router）非常简单（纯 Python 计算逻辑），不会成为瓶颈。真正的瓶颈在于：外部服务商在返回 429 报错或大幅增加延迟之前，到底能承受多大的并发流量。

### 2.1 动机

- 每个服务商（如 FreeInference, Together, Groq, SambaNova 等）都有自己未公开或未完全公开的频率限制（RPM/TPM/并发数）。
- 当网关向服务商发请求时，我们需要知道其**真实可持续的请求速率**，以免在实验途中触发限流。
- 不同模型的限流策略不同——服务商可能会给 `llama-3.3-70b` 分配极高的并发额度，但给冷门模型的额度极低。
- 根据 Juncheng 的建议：**我们应该将实验范围缩小到 1-2 个在多个平台上都具备高容量（High capacity）的大模型上**，从而确保我们在不同服务商之间有足够的调度空间。

### 2.2 模型选择

重点考察在多个服务商上都可用，且容量相对较高的模型：

| 模型 | FreeInference | Together | Groq | SambaNova |
|-------|--------------|----------|------|-----------|
| llama-3.3-70b-instruct | 是 (占流量 59%) | 是 | 是 | 是 |
| llama-4-scout | 是 (占流量 13%) | 是 | 待定 | 待定 |

**主力模型**：`llama-3.3-70b-instruct` —— 它在我们的数据集中流量最大，且各大主流平台均有部署，获得的算力容量通常也是最高的。

**备用模型**（可选）：`llama-4-scout` —— 流量第二高，可用于验证多模型混合调度的泛化性。

### 2.3 摸底测试方案

针对每一种 (模型, 服务商) 的组合：

**第一阶段：基线摸底 (Baseline Profiling)**
- 发送单并发的串行请求（迭代 50+ 次）。
- 测量在“零资源竞争”下的基线 TTFT（首字延迟）、TPS（吞吐量）和总延迟。

**第二阶段：限流边界探索 (Rate Limit Discovery)**
- 逐步拉高请求频率：1, 2, 5, 10, 20, 50, 100 RPM（每分钟请求数）。
- 在每个频率梯度下发送一批请求，并记录：
  - 成功率（2xx 状态码 vs. 429 / 503 / 响应超时）
  - TTFT 的分布情况（P50, P95, P99）
  - HTTP 响应头中的限流字段（如 X-RateLimit-Remaining, Retry-After 等）
- 找出每个服务商针对特定模型的**最大可持续 RPM**。

**第三阶段：持续高压测试 (Sustained Load)**
- 按照探索出的“最大可持续 RPM”的 80%，进行 1 小时的持续高压请求。
- 重点监控：
  - 延迟随时间的漂移（服务商是否会在持续高负载后悄悄限流？）
  - 间歇性的 429 报错或配额刷新行为
  - 细粒度 Token 吞吐率的稳定性

### 2.4 需要收集的核心指标

| 指标 | 目的 |
|--------|---------|
| 每个 (模型, 服务商) 的最大 RPM | 设定正式实验中的可行请求速率 |
| 429 报错的触发临界点 | 决定安全运行的工作点 |
| 限流的统计窗口和重置周期 | 辅助对齐我们的配额统计窗口 |
| 满载状态下的 TTFT | 验证真实负载下延迟模型是否依然成立 |
| 并发限制 (如适用) | 为 $S_C$ 模型设定参数 $C$ |

### 2.5 预期交付物

1. 一份“限流图谱表”：包含所有 (模型, 服务商) 组合的安全 RPM 阈值。
2. 模型选择建议（敲定 1-2 个在跨平台调度中容量表现最好的模型）。
3. 执行决策（Go/no-go）：选定的服务商提供的聚合吞吐量，是否足够支撑起一次有意义的在线实验？

## 3. 在线实验计划

### 3.1 从历史回放升级为在线服务

根据导师建议：我们不再使用重放历史数据的跑法，而是搭建一个**真实的在线实验（Live online experiment）**。由 Primal-Dual 路由器在真实的 FreeInference 平台和按量付费的商业 API 之间，实时做出路由抉择。

**架构设计：**

```
用户请求 (受控回放或真实流量)
       |
       v
+------------------+
| RouteWise Router |  <-- 运行 Primal-Dual / LA-PD 决策引擎
+------------------+
       |
   +---+---+
   |       |
   v       v
  S_Q     S_A
(FreeInference)  (Together / Groq 等)
```

相比历史回放，最大的区别在于：网关将**真正地发起网络请求**，并观测到真实的延迟、真实的 Token 数量，并处理真实的线上报错。

### 3.2 为什么用 FreeInference 扮演 $S_Q$

FreeInference 为选定的模型提供免费推理服务。在我们的理论框架中：
- **$S_Q$ (配额订阅)**：FreeInference 隐式包含了每日/每小时的调用限制。我们还可以人为在系统里加上每天 $Q$ 次请求的“硬上限”，以制造可控的稀缺性。
- **$S_A$ (按量付费)**：由 Together AI, Groq 等服务商扮演兜底渠道。
- **成本指标计算**：省下的钱 = 分配给 $S_Q$ 的请求数 $\times$ (对应 API 的单价)。

### 3.3 模型选取 (基于 Juncheng 的建议)

将实验严格限制在 **1-2 个在各大服务商上都具备高容量的模型**上，以确保在不同服务商间切换时不会触发封控：

- **主力模型：llama-3.3-70b-instruct** —— 占据 FreeInference 59% 的流量，并且在 FreeInference / Together / Groq / SambaNova 均有部署。拥有最高的算力保障。
- **备用模型 (可选)：llama-4-scout** —— 占据 13% 的流量，可用于验证多模型的泛化能力。

这种做法直接避开了使用冷门模型（如 GLM-4.5 或 MiniMax）带来的风险：这类模型在 API 端的容量太低，一旦并发上来，实验就会因为“触碰 API 限流”而中断，根本等不到“订阅配额 ($Q$) 耗尽”这一实验核心要素发生。

### 3.4 流量源策略

**面临的问题**：原始的 FreeInference 流量波动极大，在大多数日子里太过稀疏。

**解决方案**：采用**附带速率缩放的受控回放（Controlled replay with rate scaling）**：
1. 从历史日志中，挑出流量最大的 18 天（每天请求数 > 2K）。
2. 在实时系统中，以真实时序向后端发起这些请求。
3. 把回放的发送速率压制在第 2 节摸底出来的“安全 RPM”以内。
4. 人为设定每日配额 $Q$，人为制造资源的“稀缺感”：
   - 设定 $Q = 300$ (Base 级别)：约 50% 的高流量日会触发配额短缺。
   - 设定 $Q = 2000$ (Plus 级别)：约 30% 的天数会触发配额短缺。
   - 设定 $Q = 5000$ (Pro 级别)：约 25% 的天数会触发配额短缺。

### 3.5 实验设计总览

| 参数 | 设定值 |
|-----------|---------|
| 持续时间 | 7 天 (从历史中截取连续 7 个高流量日) |
| 评测模型 | llama-3.3-70b-instruct (主力) |
| $S_Q$ 提供方 | FreeInference (通过网关施加硬性 $Q$ 限制) |
| $S_A$ 提供方 | Together AI (按量付费，确保无并发瓶颈) |
| 配额梯度 | $Q \in \{300, 2000, 5000\}$ |
| 请求下发速率 | 严格控制在摸底探测出的安全 RPM 之内 |
| 路由策略 | Greedy, Primal-Dual (EMA), LA-PD (P10), Offline Optimal (事后分析) |
| 评价指标 | 总花销 ($), 成本节省比例 (%), 配额利用率, 首字延迟 TTFT (P50/P99) |

### 3.6 在线实验专属监控指标

除了经济成本外，真实的在线系统还能测量：

1. **端到端延迟对比**：比较路由到 FreeInference 和 Together AI 的真实 TTFT。这能证明“我们省下来的钱，并不是以牺牲用户延迟体验为代价换来的”。
2. **服务商可靠性**：记录真实的错误率、重试次数和超时率。
3. **决策引擎耗时**：测量网关执行路由算法本身消耗的时间（理论上应 $<1\text{ms}$）。
4. **生成长度预测在生产环境的准确率**：在真实的生成环境下，对比我们的 P10 预测结果和 LLM 最终输出的实际 Token 数。

### 3.7 执行步骤

1. **[限流摸底]** 对 `llama-3.3-70b` 在 FreeInference 和 Together AI 上的限流阈值进行探底 (见第 2 节)。
2. **[网关埋点]** 在网关侧加入请求级日志：时间戳、路由决策、服务商、TTFT、TPS、Token 消耗、算力成本、错误码。
3. **[配额管理器]** 实现一个实时的内存/Redis 配额追踪器，用来严格拦截超过 $Q$ 的请求。
4. **[路由引擎集成]** 把用 Python 写的 Primal-Dual 策略连通到发送 HTTP 请求的客户端代码中。
5. **[带量压测 (Dry Run)]** 先试跑 1 天 ($Q=2000$)，打通整套数据流水线。
6. **[正式实验]** 执行完整的 7 天在线打流实验（覆盖所有 $Q$ 的梯度）。
7. **[事后对比分析]** 把线上实际跑过的请求日志拿下来，喂给 Offline Optimal 算法算出理论下界，作为对比基线。

### 3.8 预期结果

基于之前脱机跑出的结果 (参考 `stage1_comparison.json`)：

| 数据集 | 模拟套餐 | 贪心算法节省 | Primal-Dual 节省 | 离线最优节省 |
|---------|------|---------------|------------|-----------------|
| BurstGPT | Base (Q=300) | 1.4% | 2.5% | 5.4% |
| BurstGPT | Plus (Q=2000) | 10.0% | 16.0% | 22.7% |
| BurstGPT | Pro (Q=5000) | 20.2% | 29.8% | 38.5% |
| FreeInference | Base (Q=300) | 37.4% | 42.8% | 56.8% |
| FreeInference | Plus (Q=2000) | 46.7% | 54.6% | 63.1% |
| FreeInference | Pro (Q=5000) | 38.6% | 46.2% | 56.9% |

在线实验应该能复现类似比例的资金节省。更重要的是，我们现在可以附上一张“真实的延迟监控图表”，证明这套系统能端到端（End-to-End）稳定运行。
