# RouteWise Real-Eval Pilot Demo

Date: 2026-05-09  
Goal: show whether the real online evaluation path works end-to-end, and whether `RouteWise p75 + hedging` is already a good live headline.

## TL;DR

Infrastructure works. The real-eval runner can run RouteWise and OpenRouter baselines on the same trace, collect TTFT/cost/failure/rate-limit/provider-mix metrics, and finish a 1h pilot.

Result is not yet a clean paper headline. RouteWise beats OpenRouter auto and sort-price on latency, but loses clearly to OpenRouter `sort_latency`.

Important caveat: this run used the trace's true `num_decode_tokens` as the routing-time completion token budget. That is an oracle output-length signal, not the intended live predictor path. Treat this as an infrastructure pilot, not as a final predictor-based real experiment.

## What We Ran

Trace:

- `data/real_eval/burstgpt_day2_h17_1h_n500.jsonl`
- 500 requests, BurstGPT day2 17:00-18:00 deterministic downsample

Inventory:

- `experiments/real_evaluation/data/pilot_chutes_featherless_rw6_1h_fair.json`
- `Chutes_SQ`: 208 requests / hour, fair projection of 5000/day
- `Featherless_SC`: concurrency limit 1
- OpenRouter filtered to 6 providers: Chutes, Inceptron, DeepInfra, AtlasCloud, Friendli, SambaNova

Policies:

- `budget_range_p75_hedge`
- `openrouter_auto`
- `sort_latency`
- `sort_price`

Profile maintenance:

- warmup: 5 samples/provider, 180s between rounds
- periodic probing: every 180s
- profile window: 15min
- request timeout: 60s
- SLO: 2000ms

Output-length handling:

- routing used trace truth: `completion_tokens_budget = num_decode_tokens`
- API `max_tokens` also used the same trace value
- no online output-length predictor was wired into this real-eval run
- before a result-oriented rerun, routing should use a predictor estimate and the artifact should record predictor metadata

Artifacts:

- `outputs/real_eval/pilot_1h_p75_vs_openrouter_fair_20260509_203451/summary.json`
- `outputs/real_eval/pilot_1h_p75_vs_openrouter_fair_20260509_203451/requests.csv`

## Main Results

TTFT metrics are computed over successful requests. Cost below is API metered cost from `summary.json`; this includes replay traffic only, including RouteWise hedge backup requests when they were dispatched. It does not include warmup/periodic probing traffic.

|---|---:|---:|---:|---:|---:|---:|---:|---:|

| OpenRouter auto | 499/500 | 2424ms | 1866ms | 4396ms | 8548ms | 46.6% | $0.0477 | 0 |
| OpenRouter `sort_latency` | 499/500 | 1225ms | 1105ms | 1484ms | 4125ms | 2.4% | $0.0519 | 0 |
| OpenRouter `sort_price` | 500/500 | 1779ms | 1449ms | 2607ms | 10651ms | 12.4% | $0.0366 | 0 |

Cost interpretation for RouteWise:

```text
$0.063 API cost
  = replay metered API cost from requests.csv / summary.json
  = includes RouteWise primary + hedge backup replay requests
  = excludes warmup and periodic probing

$0.126 effective cost
  = $0.063 replay API cost
  + $0.0278 Chutes 1h fixed cost       ($20 / 30 / 24)
  + $0.0347 Featherless 1h fixed cost  ($25 / 30 / 24)
  = $0.1258
```

Probe cost caveat:

- warmup: 5 rounds x 8 providers = 40 probe requests
- periodic: 16 rounds x 8 providers = 128 probe requests
- total profile-maintenance probes observed: 168
- of these, Chutes probes = 21, Featherless probes = 21, OpenRouter probes = 126
- current `summary.json` does not persist probe cost
- rough OR probe metered-cost estimate from terminal logs: about `$0.002-$0.005`
- direct Chutes/Featherless probes have `$0` API metered cost, but still consume real service capacity / rate-limit budget

## Hedging Behavior

RouteWise:

- hedge triggered: 303/500 requests
- backup won: 69/303 hedges
- backup win rate: 22.8%
- rate-limited chosen requests: 15
- total retry sleep: 16.75s
- replay dispatches sent by RouteWise: 803 total = 500 primary + 303 backup
- Chutes replay sends: 130
- Featherless replay sends: 16

Interpretation:

- Hedging is active and observable.
- In this slice, hedging was probably too aggressive: it increased API cost and did not beat `sort_latency` tail latency.
- Some hedge/retry pressure hit Inceptron, Chutes, and Featherless during bursts.

## What Worked

- Real runner completed a full 1h pilot.
- OpenRouter provider filters worked.
- Warmup and periodic profile probing worked.
- Metrics were collected for latency, cost, errors, rate limit, provider mix, and hedging.
- Chutes hourly fair quota was enforced locally as 208/hour rather than using the full 5000/day bucket.

## What Did Not Work Yet

- Output-length prediction is not wired into real-eval yet. Current RouteWise routing uses oracle trace output length, so the run has data leakage for cost-layer decisions.
- RouteWise did not beat OpenRouter `sort_latency`.
- RouteWise had 1 error and 15 rate-limited chosen requests.
- `sort_latency` had much better P90/P99 in this slice.
- Profile-maintenance probe 429s are not summarized in `summary.json`; they affect profile but are not visible as a separate metric.
- Probe cost is not summarized in `summary.json`; for this run it is small, but we should persist it before final experiments.

## Suggested Discussion With Juncheng

1. Is `sort_latency` the right live baseline to beat for the first real experiment, or should the headline be RouteWise vs OpenRouter auto / sort-price?
2. Should we tune RouteWise for live runs away from `p75_hedge`? Candidate next runs: `p50_hedge`, `p75_no_hedge`, or lower hedge target.
3. Should final real-eval cost include hourly fixed subscription cost, or show both API-only and effective cost?
4. Should profile-maintenance probe failures/rate-limits be added to summary metrics?
5. Should we pick a different 1h trace slice where subscription capacity matters more and `sort_latency` is less trivially strong?

## Current Recommendation

Use this run as a demo that the live infrastructure works, not as the final result.

For the next result-oriented run, try one of:

- Wire an online output-length predictor into real-eval before rerunning. Use predicted tokens for RouteWise routing cost estimates; keep the trace output cap only as the API generation cap if we want every policy to face the same workload.
- RouteWise `p50_hedge` or lower hedge target to reduce over-hedging.
- RouteWise `p75` without hedging to isolate routing from hedge overhead.
- A trace slice selected from simulator where RouteWise beats `sort_latency` or where `sort_latency` has higher tail risk.
